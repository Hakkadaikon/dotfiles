# 作業の進め方

工程は superpowers、検証とgit運用の差し込みは hymme(セッション開始時に注入される using-hymme の地図)に従う。ここには両者に無い個人方針だけを置く。

## コミット

- git 管理下の変更は作業完了時に未コミットで残さず、`hymme:commit-flow` で粒度を決め `hymme:micro-commit` でコミットする。ユーザーが単一コミットを明示したときは従う。
- 検査(lint、テスト)とコミットを、同時に出す道具の呼び出しに分けて入れない。検査の終了コードを見てから、次の呼び出しでコミットする。並べて出すと、検査が落ちてもコミットが走る。

## 自律修正

- バグ報告を受けたら、手取り足取りを求めず自分で直す。ログ、エラー、失敗テストを手がかりにする。
- 直す前に `hymme:escape-flow` で欠陥の記録を開く。実物で再現し、拾えたはずの前の段にテストを足してから閉じる。
- ただし superpowers:systematic-debugging の「修正が3回失敗したら止めて相談する」は守る。
- CI の失敗は指示を待たずに直す。user の context switch を最小にする。

## 提出前

- 自分の成果物を一度疑う。熟練エンジニアがこれを承認するかを自問する。
- 完了と言う前に、実物で動かして確かめる(`hymme:real-surface` の確認のコマンド)。テストが通ることは、動くことの代わりにならない。

## hymme の検査に止められたとき

- 表示された手順に従う。検査をよける別の経路(スクリプトに包む、別名で呼ぶ、記録の置き場に触る)を探さない。
- 作業者の承認が要るときは、申請の中身と符号を示して、そこで止まる。承認の入力(`承認 <符号>`)は自分では行わない。
- 例外の申請(`hymme exception request`)は最後の手段にする。先に検査を満たす方法を試し、申請するなら期限を短くし、理由に「なぜ満たせないか」を書く。
- 止められた事実と、迷った点は、最後の報告に書く。検査の側の誤りだと思ったら、よけずにそう報告する。
- 承認が記録されない、検査の文言が手順書と合わないときは、プラグインと skill-tools のバージョンの食い違いを疑う(dotfiles の `env.sh` の profile の手順が両方を揃える)。
